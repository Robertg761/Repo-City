Everything below was run against the **live production deployment**,
<https://repo-city-five.vercel.app>, not a local build: the streaming API through
`GET /api/analyze?repo=`, and the application through headless Chromium at 1600 x 1000
driven over the Chrome DevTools Protocol.

error copy. No code was changed as part of this pass. Bugs are listed at the end with a
severity and the file that most likely owns them.

**591 tests in 39 files, all passing**, `pnpm build` clean (routes: `/`, `/_not-found`,

history except PLAN.md's own description of the scan and a clearly fake `ghp_supersecrettoken`

All eight happen. The core experience works.

**Confusing or rough, in order of how likely a voter is to hit it:**

1. At close inspection range an incident reads as roadworks — barriers and a dark wedge — more
   than as a crash. Since construction is also a metaphor in this city (cranes), the two can
   momentarily blur. The legend entry and the inspector resolve it, but the shape does not.
2. The example repository in the empty state (`github.com/facebook/react`) is plain text. It
   looks clickable and is not; clicking it does nothing. One click to prefill would remove the
   only dead end in the first ten seconds.
3. The district inspector reports `Buildings 24` and, two lines below, "with 63 files". Both
   numbers are true — buildings are capped and pooled — but read together they look like a
   contradiction.
4. Error recovery is good and worth keeping: a bad repository shows the section 60 copy, the
   input the user typed, a `TRY AGAIN` button and a dismiss control.

## 3. Bugs

None were fixed. Severity is about the submission, not about engineering purity.

### Bug 1 — `FIXTURE_FALLBACK` is opt-in, but was documented as defaulting to on

**Severity: high (deployment risk, not a code defect).**
Owner: `lib/github/fixtures.ts` (`isFixtureFallbackEnabled`); the wrong wording was in
`README.md` and `PLAN.md` section 30.

`isFixtureFallbackEnabled` treats an **unset** `FIXTURE_FALLBACK` as `false`, and
`lib/github/fixtures.test.ts` asserts that deliberately. `README.md` and PLAN.md section 30
both described the default as `true`.

The consequence is entirely about voting weekend: if the Vercel project does not set
`FIXTURE_FALLBACK` explicitly, then the moment GitHub rate-limits the shared token — which is
exactly what a burst of voters causes — the demo returns `GitHub is temporarily limiting
analysis` instead of serving the committed snapshots that exist for all seven demo
repositories. The safety net is present, tested, and off by default.

The behaviour is defensible (an explicit opt-in for serving stale data is a reasonable design).
**The documentation was the bug**, and I have corrected `README.md` and `.env.example` to say
that unset means off. What remains is an action, not a fix:

> **Verify `FIXTURE_FALLBACK=true` in the Vercel project's environment variables before
> submitting.** This is on the checklist in `docs/SUBMISSION.md`.

### Bug 2 — two different file counts for the same repository, both shown to the user

**Severity: medium (cosmetic, but visible and contradictory).**
Owner: `lib/analysis/metrics.ts` (`scale.files`) vs the `tree` stage detail produced in
`lib/github/snapshot.ts` / `lib/analysis/analyze.ts`.

The progress panel's `tree` line and `metrics.scale.files` report different numbers, and both
surface in the interface — the second via `lib/client/entities.ts:120`, which puts
`{ label: "Files", value: metrics.scale.files }` in the City Hall inspector.

| Repository | `tree` stage says | `scale.files` says |
| --- | --- | --- |
| `sindresorhus/p-limit` | 16 files mapped | 10 |
| `vercel/turborepo` | 2,884 files mapped (partial survey) | 2,746 |
| `microsoft/vscode` | 2,500 files mapped (partial survey) | 2,015 |
| `torvalds/linux` | 2,500 files mapped (partial survey) | 2,491 |

On p-limit the gap is also visible a third way: the curated summary in the City Hall inspector
opens "Sixteen files, no source directory", next to an inspector row reading `Files 10`.

The two are measuring different things (raw tree blobs vs. files after selection), which is
legitimate — but they are labelled identically. Either label them differently ("16 surveyed /
10 mapped") or report one number in both places.

### Bug 3 — soft shadows are silently downgraded, plus a deprecation warning on every load

**Severity: low.** Owner: `components/CityCanvas.tsx:95` (`shadows="soft"`).

Every page load logs, once per canvas:

```
THREE.WebGLShadowMap: PCFSoftShadowMap has been removed. Using PCFShadowMap instead.
THREE.Clock: This module has been deprecated. Please use THREE.Timer instead.
```

`shadows="soft"` asks react-three-fiber for `PCFSoftShadowMap`, which three.js 0.186 has
removed, so the renderer falls back to hard-edged `PCFShadowMap`. The city still looks good —
the screenshot in this repository was taken with the fallback — but the softer shadows the
lighting was tuned for are not what ships. The `THREE.Clock` warning appears to come from a
dependency rather than from project code; worth confirming before spending time on it.

Both warnings are visible to anyone who opens DevTools on the demo, which a technical voter
plausibly does.

### Bug 4 — an incident does not read as a crash at close range

**Severity: low-medium (presentation).** Owner: `components/city/IssueIncident.tsx`.

The incident assembly is a dark crater with road barriers and a brown wedge. At overview
distance it reads correctly as damage. Flown in on — which is exactly what the demo video does
at 0:20 — it reads as roadworks, and roadworks are close to the construction metaphor already
used for pull requests. PLAN.md section 11 calls for an accident scene, with smoke on severe or
highly active bugs; no smoke appeared on the stale VS Code bug tested.

Post-freeze this is a "leave it" unless the renderer agent is already in the file.

### Bug 5 — `INFORMATION CENTER` in the inspector, `Information centre` in the legend

**Severity: low (cosmetic).** Owner: `lib/client/entities.ts:38`.

`lib/client/entities.ts` uses the American spelling for the landmark label; `components/Legend.tsx:21`
and every code comment in the project use the British one. A user sees both in the same
session. One-word fix, no behaviour change.

### Bug 6 — thousands separator applied inconsistently in the same panel

**Severity: low (cosmetic).** Owner: `lib/analysis/metrics.ts:168`.

The incident inspector shows `Open  3,083 days` in the facts list and, directly beneath it,
"An unresolved bug that has stayed open for **3083** days." The facts list formats through
`toLocaleString` in `lib/client/entities.ts`; the reason string interpolates the raw number
server-side.

### Bug 7 — a handled failure is logged as a console error

**Severity: low (cosmetic).** Owner: `store/useCityStore.ts`.

A `NOT_FOUND` — a completely normal outcome — writes a red `console.error` with a stack trace
to the browser console, next to a user interface that is handling it gracefully. It looks like
an unhandled exception to anyone inspecting the demo.

### Bug 8 — incidents with no related path land on generic ring roads

**Severity: low (by design, noted for completeness).** Owner: `lib/city/generator.ts` placement.

Most `microsoft/vscode` issues carry `relatedPath: null`, so their incidents are placed on the
outer roads rather than near the code they concern. This is a reasonable fallback and the
grounding rules require it — an ungrounded path must not be invented — but it does weaken the
"this bug lives here" reading for repositories whose issues do not name files.

### Bug 9 — the first hover after a page load can produce no tooltip

**Severity: very low (near-theoretical).** Owner: `components/Tooltip.tsx`.

`Tooltip` only attaches its `pointermove` listener once `hoveredId` is set, and it needs a
`pointermove` to learn where to draw. On a freshly loaded page, the very first object hovered
therefore has no position until the pointer moves once more. Real pointers are always moving,
so this was not reproducible by hand — only by synthesising a single mouse event.

## 4. Open item that is not a bug

**The Open Graph image has no production URL.** `app/layout.tsx` now sets an `openGraph.images`
entry, but Next only serves `public/`, so `docs/screenshot.png` has no URL on
`repo-city-five.vercel.app`. The metadata therefore points at
`https://raw.githubusercontent.com/Robertg761/Repo-City/main/docs/screenshot.png`, which is
absolute, resolves, and is unambiguously the committed file.

The alternative — copying the same PNG to `public/screenshot.png` and pointing at
`https://repo-city-five.vercel.app/screenshot.png` — means committing a second copy of the same
image, which this pass was explicitly scoped not to do. If Robert prefers the self-hosted URL,
it is a two-line change: copy the file and swap the constant.

This only affects link previews when the demo URL is shared. The Hackyard project card uses the
uploaded screenshot, not Open Graph, so it is not on the critical path.
